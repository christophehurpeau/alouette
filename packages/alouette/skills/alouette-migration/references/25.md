# alouette 25

Breaking changes of 25.0.0, then what changed within 25.x without breaking:
the patch an app on React Native 0.88 needs for `react-native-css`.

## To 25.0.0

### Regenerate a custom palette: `system` is resolved in CSS

`AlouetteProvider` now applies the `system` theme instead of a mode resolved
in JS, and a `ScopedTheme` takes `"system"` / `"system_<accent>"`. The palette
CSS resolves them with `prefers-color-scheme`, so the prerendered HTML already
wears the visitor's mode instead of flashing light until hydration. A palette
generated by an older `alouette/theme-generator` has no `.system*` blocks: on
web, the whole app then renders light whatever the OS asks for. Re-run the
app's `writeTheme(...)` (or `generateTheme(...)`) script. The `themeVariables`
map is unchanged.

### Pass a stored preference to `ScopedTheme` as is

Resolving the preference in JS before applying it renders `light` on the
server, so a dark-mode visitor sees the light page until the JS runs. Pass it
as is; keep `useResolvedColorMode` for what reads the mode in JS (a status bar
style, a computed color). `ColorModePreference` is unchanged.

```tsx
// Before
<ScopedTheme theme={useResolvedColorMode(preference)}>{children}</ScopedTheme>

// After
<ScopedTheme theme={preference}>{children}</ScopedTheme>
```

`useCurrentMode`, `useCurrentTheme`, `useResolvedColorMode` and
`useSystemColorMode` still return a resolved `light` / `dark` theme. On web
they now read `light` during the server render and hydration, then the OS
mode on the next render.

Changed appearance: on web, `html` and `body` take the dark tokens while a
`system` scope is in the document and the OS is dark.

## Within 25.x — React Native 0.88 (Expo SDK 58): patch `react-native-css`

On native, the app crashes as soon as it loads a font or an asset:

```
Cannot read property 'getAssetByID' of undefined
  at fromModule (expo-asset/build/Asset.js)
```

React Native 0.88 exports `AssetRegistry`, and expo-asset 58 imports it from
`react-native`. `react-native-css` redirects every `react-native` import to its
own `react-native-css/components` module, which lists React Native's exports
by hand and does not forward `AssetRegistry` (up to `3.1.0-rc.1`), so it reads
`undefined`. Until a release includes
[nativewind/react-native-css#504](https://github.com/nativewind/react-native-css/pull/504)
([issue #506](https://github.com/nativewind/react-native-css/issues/506)),
patch the package in the app.

With pnpm, `pnpm patch react-native-css@3.1.0-rc.0`, then add the getter to
`dist/module/components/index.cjs` and `dist/commonjs/components/index.cjs`
(the `import` and `require` conditions of `react-native-css/components`), and
`pnpm patch-commit` the edit directory. With npm or yarn, `patch-package` does
the same.

```js
// Before
  get AppState() {
    return require("react-native").AppState;
  },
  get BackHandler() {

// After
  get AppState() {
    return require("react-native").AppState;
  },
  get AssetRegistry() {
    return require("react-native").AssetRegistry;
  },
  get BackHandler() {
```

Restart Metro with a cleared cache (`expo start -c`). Drop the patch once the
`react-native-css` version alouette's `nativewind` peer requires ships the fix.

## Within 25.x — Expo Router 58: the iOS header lays over the screen

On iOS 26, Expo Router 58 turns a `Stack` header with no background of its own
into a transparent glass bar laid over the content. Under it, a
`ScreenScrollView` padded only the status bar, so the first rows sat under the
header.

The screen containers (`ScreenScrollView`, `ScreenFlatList`,
`ScreenSectionList`) now pass `contentInsetAdjustmentBehavior="automatic"` on
iOS: UIKit insets the top and bottom from whatever covers the list, glass or
opaque header included, and alouette pads only the left and right edges there.
Nothing to change for an opaque header. For a screen meant to keep the glass
header (over a background image), declare its height, which Android needs:

```tsx
// Before
<SafeAreaScope consumedEdges={["top"]}>
  <ScreenScrollView>…</ScreenScrollView>
</SafeAreaScope>

// After: a transparent header (`headerTransparent: true`)
<SafeAreaScope topOverlayHeight={useHeaderHeight()}>
  <ScreenScrollView>…</ScreenScrollView>
</SafeAreaScope>
```

To keep the opaque header everywhere else, set
`screenOptions={{ headerTransparent: false }}` on the `Stack`; its ground is
then the navigation theme's `colors.card`, or a `headerStyle.backgroundColor`.

Changed behavior, on iOS only, for a container with neither `edges` nor a
`topOverlayHeight`:

- `consumedEdges` no longer removes the top or bottom inset: what covers the
  list decides. A screen that consumed the top to draw under the status bar
  passes `edges={["bottom", "left", "right"]}`.
- The top and bottom insets are a content inset, no longer a padding of the
  content container: a ground set with `contentContainerClassName` stops at the
  inset, and `contentOffset.y` is negative (minus the inset) at the top of the
  list.
